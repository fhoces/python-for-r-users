Exports that never change by accident.

The second job of the runner is to write tables to text files, and it has one rule: two runs, on any machine, in either language, must write identical files. Identical byte for byte. That rule is what makes a parity check between R and Python possible, and it is what makes a diff in git meaningful. Three decisions get you there.

First, sort by a key, every time. A SQL table has no guaranteed row order. The order you see is whatever the database found convenient, and it can change when an index is added or the data grow. So the runner keeps a dictionary called EXPORT ORDER, which maps each table to an order by clause. The year-end lists sort by date, then worth from largest to smallest, then forbes id. The forbes id is a tie-breaker: two people with the same worth on the same date always come out in the same order. A table with no entry is sorted by all of its columns. The export query always includes the order by. The R twin keeps a copy of the same dictionary, and a comment in each file says to keep the two in step.

Second, write floats with repr. In Python, repr of a float is the shortest text that reads back as exactly the same number. Zero point one prints as zero point one, not as a long tail of digits. That matters in two directions. Write fewer digits, as a format with six decimals would, and you lose information: the value read back is not the value you had. Write more digits than needed, and the file changes when nothing real has changed. Repr is exactly enough. Pandas' to c s v, with a float format, or an f string with a fixed number of decimals, both break this rule.

Third, small things about text. Null is written as an empty field. The C S V writer is created with a line terminator of a single newline, so the file is the same on every operating system. And the file is opened with newline equals an empty string, which stops Python from translating line endings on its own.

Now the R side, which shows how hard the second rule is. R has no repr. The R twin writes each double with fifteen significant digits, checks whether that text reads back as the same number, and if not tries sixteen, then seventeen. It also adds point zero to numbers that would otherwise look like integers, because Python's repr does. Even so, R's text-to-number conversion is not always correctly rounded in the sixteenth digit. So now and then R writes seventeen digits where Python writes sixteen. The two files then differ as text while holding exactly the same numbers.

That is the reason the parity check, the fourth drill, never compares the two files as text. It reads both as text, and wherever a cell parses as a number on both sides, it compares the numbers. Only cells that are not numbers are compared as text. In the real run, the R and Python exports agreed to a difference of exactly zero, on every number, which is the result a text comparison could not promise.
