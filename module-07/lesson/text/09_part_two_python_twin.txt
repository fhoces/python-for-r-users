Part two: an R pipeline and its Python twin.

Everything so far was the Python around one SQL file. The same repository has a bigger piece of Python: a twin of a whole R pipeline. The paper's second step goes from the public workbook, a spreadsheet, to every number in the paper's tables and figures. That step was written in R first. Then it was written again in Python, file by file, and the two are compared number by number. The Python is not there to replace the R. It is there to check it. So it is written to be compared, not to be clever.

Start with the rule that makes the comparison possible: one Python file per R file, with the same function names. The R file for reading cells defines a function called x l s cell, and so does its Python twin. The R file for the Pareto sheet defines compute pareto missing, and so does the Python one. A data frame keeps the R column names in the R order. An R named list becomes a Python dictionary with the same keys. Where the R code reproduces an odd spreadsheet rule, the twin reproduces the same odd rule. And a script called run export plays the part of the R targets pipeline: it calls everything in order and writes one folder of results.

Two habits help when you read such a twin. First, R counts from one and Python from zero. In a panel that starts in 2018, the 2021 value is element four in R and element three in Python. The real files keep the R index in a comment wherever it matters, so a reader can hold the two side by side. Second, the twin says out loud what it does not copy: the styling of tables and the drawing of figures stay in R. The numbers behind them are twinned, because the numbers are what you check.

Now the first translation problem: reading the spreadsheet. The R side reads many sheets by position. Its read sheet function returns the whole sheet with columns named A, B, C, and rows numbered as in Excel, so the cell G16 is column G, row sixteen. The Python twin does the same with a library called open p y x l. It opens the workbook with data only set to true, and read only set to true. Data only matters. A cell with a formula holds two things: the formula, and the number Excel last computed. R's reader returns the number, so the twin must ask for the number too. Without data only, you would get the text of the formula. And if a file was written by a program that never calculated it, there is no stored number at all, and you get None.

Then the twin walks the rows, keeps the raw values, and builds a data frame whose columns are the Excel letters and whose index starts at one, not zero. That way the Python line that reads G16 looks like the R line it mirrors. Two habits of R's reader have to be copied by hand. It drops empty rows and columns at the end of a sheet, and a formatted but empty cell at the bottom is enough to make open p y x l report extra rows. And it reports a date, in a text column, as a plain serial number: the number of days since the end of 1899. December 31, 2018 becomes forty three thousand, four hundred sixty five.

The second translation problem is turning a cell into a number. In R, a mixed column arrives as text, and the code calls as numeric, with the warnings silenced. Anything that is not a number becomes missing. Python's float function looks like the same thing, and it is not. Float accepts a number written with an underscore, like one underscore zero zero zero, and returns one thousand. R says missing. Float of true is one. In R, a true cell arrives as the text true, and becomes missing. And float raises an error on a label, where R quietly says missing. So the twin has its own small function, to num, that returns not a number in every case where R would say missing. Drill six grades exactly those cases.

The third problem is the everyday R idioms. Percent in percent becomes is in, and the negation is the tilde, not the word not. R's duplicated, negated, becomes the pandas method duplicated, with a subset of columns and keep set to first. Leave the subset out, and pandas compares every column, so a copy with one re-typed cell survives. R's n, the number of rows in a group, becomes size. The pandas count method is a different thing: it counts values that are not missing, like count of a column in SQL. And R's sum with n a dot r m equals true becomes the pandas sum, which skips missing values and gives zero for a group where everything is missing. Ask for min count of one, or use numpy's plain sum, and you get not a number instead. Drill seven is the twin of a short dplyr pipeline that does all of this, and it is graded against the SQL file that later replaced that pipeline. Three implementations, one answer.

A few more pairs show up in the real files. R's c of x minus one, and zero, drops the first element and pads with a zero. In Python, x minus one is the last element, so the twin writes a slice from one, then appends the zero. And R's sequence from zero to point two by point zero zero one is computed as a start plus a whole number times the step. Numpy's arange stops before its end point, so from zero to point two it gives two hundred values where R gives two hundred and one. And with a start other than zero, it rounds the step once and can change the last digit. The twin writes R's formula directly, so the two give the same doubles.

The last piece is the parity test, the reason the twin exists. The Python pipeline writes every number to a folder. An R test reads each Python file next to its R counterpart and compares them. It is strict about everything except the last digits. Column names must match. Row counts must match. Missing values must sit in the same cells: missing in R and a number in Python fails, whatever the tolerance. Text must match exactly. And a Python file with no R counterpart fails too.

For numbers it uses a relative tolerance: the absolute difference must be at most one in a billion times the larger of one and the R value. Why relative? Because one unit in the last place grows with the number. A dollar total near two trillion has a last place of about two ten thousandths, so an absolute tolerance of one in a billion would fail on pure rounding. Why the floor of one? Because some outputs are near zero on purpose, like a check that should be zero and holds a tiny leftover. Divide a tiny gap by a tiny number and you get a huge relative difference that means nothing. And why one in a billion? The real gaps come from three harmless places: how R parses seventeen digit text, R's mean taking a second correction pass, and numpy adding in pairs. They are around one part in ten to the sixteenth. A real mistake moves a number far more than one in a billion.

Two more habits are worth copying. The test skips, rather than fails, when the Python folder is missing, so someone running only R is not blocked. And the Python folder is committed, so the test can run on a machine with no Python at all. On the day it was written, fifty outputs and almost fifty four thousand numbers agreed to within five parts in ten to the fifteenth.

That is part two. Mirror the R file function by function. Read cells the way R reads them. Translate each idiom with its trap in mind. And compare with a test that is strict on everything except the last digits.
